# ROI+ 期待値と自律学習の確認

確認日: 2026-10-10 JST。監査対象は本番の読み取り画面、既存モデルのメタデータ、ローカルの実データ集計と実装。監査は読み取りで行い、その後の改善の本番反映は別途ユーザー承認のもとで実施する。実購入は行わない。

## 結論

**現状では実際の期待値がプラスだと確認できない。** 画面の「期待収益率」はモデルの確率と取得時オッズからの推定であり、利益の実証ではない。アプリは仮想運用専用で、実際の投票機能もない。

本番画面を「実データ」に限定すると、確認時点で仮想購入19件、精算済み0件、損益0円、回収率未算出だった。表示上の稼働モデルは `boat-win-lgbm-v1`。結果待ちの購入は、成功・失敗のどちらにも数えられない。

## 既存モデルの根拠と限界

`ml/artifacts/boat-win-lgbm-v1.json` の保存値:

| 項目 | 値 |
|---|---|
| 学習期間 | 2026-07-01 から 2026-09-09 |
| 学習レース | 10,975件 |
| 検証期間 | 2026-09-10 から 2026-09-24 |
| テスト期間 | 2026-09-25 から 2026-10-09 |
| テストレース | 2,147件 |
| Log Loss | 1.1883、コース別基準 1.3093 |
| Brier | 0.5802、レース単位の多クラス定義 |
| ECE | 0.0171 |
| 回収率・期待収益率・最大DD | いずれも欠損 |

確率の精度と賭けた場合の収益性は別の指標である。[scikit-learn の校正文書](https://scikit-learn.org/stable/modules/calibration.html)も、Log Loss と Brier は校正だけでなく識別能力と結果の不確実性を含めて評価すると説明している。

既存モデルには再検証が必要な時点リークの経路がある。特徴量生成は展示・気象情報を既定で除外する設計だが、元の出走行を再結合することで `exhibition_time`・`start_exhibition` などが学習入力へ残っていた。行全体の `available_at` だけでは、後から取り込まれた個別特徴量の利用可能時刻を保証できない。既存 v1 の上記指標を、リークを修正したモデルの精度や利益の根拠として流用しない。

ローカルの実データキャッシュは15,588レースに対してオッズ24行・4レースのみ。別の推論用保存データにはオッズがなく、ローカルに仮想購入履歴もない。これは本番D1の全件数ではないが、手元で収益性を検証するには締切前オッズの履歴が不足している。勝者の払戻から敗者のオッズを補完してはいけない。

## プラスの期待値を検証する条件

- 予測時点で利用可能だった実データだけで学習・推論する。結果判明後に作った過去予測は、運用実績から除く。
- モデルと候補選択ルールを固定し、その後の未学習期間で検証する。閾値の調整に使った期間を独立テストとして再利用しない。
- 購入判断時の全対象のオッズ、予測、選択ルール、確定結果・払戻を保存する。勝った購入だけで評価しない。
- 実回収率、損益、最大ドローダウン、日付単位の不確実性を確認する。件数の下限は安全上の足切りであり、それを満たすだけで利益が保証されるわけではない。
- 締切までのオッズ変動も考慮する。[公式のオッズ表示](https://www.boatrace.jp/owpc/pc/race/oddstf?hd=20260809&jcd=24&rno=6)も、締切時オッズとレース開始後の返還等による変動を区別している。

## 自律改善の境界

「1回外した＝判断が間違い」ではない。確率予測は、多数の確定結果に対する Log Loss・Brier・校正傾向で評価する。自動処理はフィードバック集計、再学習、同じ未学習期間での候補比較までとし、稼働モデルの置換は人が承認する。

実装した処理、ローカル実行方法、運用開始に必要な条件は [自律学習](LEARNING.md) を参照。既存 v1 は自動で書き換えず、新しい候補を別IDで保存する。学習の実行成功と、モデルの改善、利益の確認はそれぞれ別の状態として扱う。

## 追加した改善と確認

- 後日情報が入力へ残る経路を修正し、旧schemaのartifactは推論・利益検証から除外した。手元の実データに対する `feedback` 実行でも、旧v1は `excluded_unverified_or_legacy_feature_schema`、評価対象0レース、ROI未証明となった。
- 日次の結果フィードバック、増分に応じた週次候補学習、同じholdoutでの比較、再実行時のstate回復とレポート保存を追加した。候補同期の失敗では学習済みcheckpointを進めない。
- 人が承認した稼働モデルを認証付きレジストリで確認する。候補の同期で稼働・退役モデルを上書きせず、比較不能・不改善の候補は画面とAPIで昇格を拒否する。
- 未来・締切後の予測、10分を超えて古いオッズ、出所の異なるデータを購入判断に使わない。後日予測は校正集計から除く。
- 成績画面に推定期待値と実収益の区別を明示した。ローカルの隔離サンプル環境で、実データ0件の場合の注意表示も確認した。

API回帰テスト27件に加え、追加ガードの対象テスト、Webの対象テスト6件、MLの対象テスト25件、型検査・Webビルドを担当範囲ごとに確認した。実データによる利益の証明は未解決であり、これらのテスト成功を代替証拠にしない。

## 設計と実装の既存差分

SPECのオッズ取得窓は25分、Worker実装は15分。SPECの最大30リクエストと、実装の最大30対象レース・再試行込み最大49 fetchにも差がある。また取得許諾についての説明とリポジトリの有効フラグには差がある。今回はこれらを推測で変更せず、収集許諾や稼働環境の設定も確認済みとは扱わない。`docs/SPEC.md` は変更していない。
