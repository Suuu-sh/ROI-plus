# 三連単の事前データ・候補学習パイプライン

## 運用と安全境界

- 実投票・課金設定変更・モデルの自動昇格は行わない。候補の学習と本番モデル昇格は別操作で、昇格前に人手承認が必要。
- 日次同期は当日のデータと、前日の未精算の実データ仮想購入に必要な入力を優先する。前日の全量結果をD1へ再送しないが、ローカルの収集・学習履歴は保持する。未精算対象の照合APIが利用できない場合は同期前に停止する。
- 日次予約の上限（合計20,000、essential16,000、optional4,000 unit）と不明時の停止を維持する。使用済み予約の返却、カウンターのリセット、自動増額は行わない。これはWorker内の推定予約で、Cloudflareの実際のアカウント全体のquotaとは別。

## 締切前データ

既存の毎分Cron・共有fetch上限・3秒以上の取得間隔を維持し、公式レーサーリスト・直前情報・非確定120組の三連単オッズを照合する。入力の到着時刻は公式締切の10分前から60秒前までに限定する。6艇の登録番号、展示情報と気象、開催日・場・レース番号、本文SHA-256が揃わないものは保存しない。

成功したレースは1つの不変JSONアーカイブとして保持する。120組オッズを行ごとに保存する前にコンパクトな証跡収集を優先し、三連単の稼働モデルがない場合はライブ購入用120行の保存を行わない。取得対象や予算制限による未取得があり、全レース取得を保証しない。

Bファイルの事前特徴量は、実際に新規取得した元バイト列のハッシュと到着時刻を記録する。昔のキャッシュへ現在の到着時刻を割り当てたり、レーサー番号が一致しただけで過去の特徴量の事前到着を証明したりしない。締切後に到着した値は過去の予測に使わない。

日次B/K同期の最初の定期実行は、日次予約のリセット後の09:05 JSTで、GitHub Actionsの遅延・欠落に備えて09:30、11:00、13:00にも再試行する（設定根拠: `.github/workflows/daily.yml`）。09:05の起動・完了時刻は保証されない。同期前に三連単アーカイブ収集の対象窓（公式締切T-10分からT-60秒）が過ぎたレースは、後から現在時刻を到着時刻として付け直さず、学習用の事前証跡にも含めない。したがって朝の定期実行が動いても当日の対象レースや証跡が得られる保証はない。

## 候補学習・検証

`.github/workflows/trifecta-candidate-pipeline.yml` は毎日23:50 JSTと手動実行で、認証付きの既存アーカイブexportを読み、ローカル履歴へ検証済み入力を取り込む。既存日次・学習ジョブと同じconcurrencyを使い、学習キャッシュの競合を防ぐ。

- 本番DBへのモデル書込・昇格を行わない。
- 取得範囲・ページ・応答サイズを制限し、出典不明や不完全な入力を除外する。
- 事前証跡を持つ実データのみを使う。最低300学習レースに加え、独立した時間順holdoutとして最低400レース・7開催日を含む検証条件や、完全な120組確率など既存条件を下げない。アーカイブ数や日次ジョブの成功だけでは学習・候補適格性を保証しない。
- データ不足はレポートに明示する。ジョブの正常完了は候補モデルの生成・適格性・利益を意味しない。
- 生成した候補artifactは実体のハッシュと実行・commitのprovenanceを照合して保存する。独立検証を通ったとしても、本番昇格は改めて人が判断する。

SPECには単勝中心の設計が残っており、三連単専用の実装・追加取得元・頻度との相違がある。SPECはこの変更で書き換えていない。
